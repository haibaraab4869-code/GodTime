## 测试策略：四层覆盖

| 层次 | 执行重点 | 记录与证据 |
| --- | --- | --- |
| 自动测试 | 规则逻辑与边界条件优先；有场景后补交互/集成测试。框架、命令与 CI 方案待开发规范确认，不预设已安装插件。 | 测试源文件及运行命令、环境、退出状态和失败日志；测试路径待框架确定后登记。 |
| 手动用例 | 输入、UI、碰撞/过渡、画面与音频等依赖体验或视觉判断的项目；覆盖正常路径、异常操作和边界情况。 | `docs/qa/test-cases/`：按功能写步骤、预期、实际与证据链接。 |
| 烟雾测试 | 每个可运行构建先验证项目启动、进入主流程、核心操作及退出；具体清单必须依已批准的玩法范围与已实现功能制定。 | 每次记录构建标识、Godot/平台、执行者、时间、逐项结果和阻塞项；不能仅写“看起来正常”。 |
| Playtest | 在可试玩版本上分别观察首次上手、关键路径理解、操作反馈、难度与卡点；不以 QA 代替玩法设计签收。 | `docs/qa/playtests/`：记录版本、受试者范围与同意情况、任务、观察、原话/数据、结论与待验证假设。 |

用例应映射到权威设计文档的**具体规则与验收标准**。规则未确定时标注“待设计确认”，不自行补写玩法或数值。修复缺陷时补相应回归用例；不稳定（flaky）测试隔离并登记原因，不能把偶发通过当作持续通过。

## 入场条件与验收门

**测试入场：**有可识别构建/提交及运行环境；对应需求或设计有可检验的验收标准；测试数据与操作入口可用；执行者明确。缺任何一项则标注 `BLOCKED` 并列明缺口，而非推断结果。

**用例判定：**逐条写 `PASS`、`FAIL`、`BLOCKED` 或 `NOT RUN`。失败须关联缺陷编号与证据；未执行和阻塞不计通过。自动测试要保留真实命令、版本、退出码与输出摘要；手动测试须有实际观察而非只填预期。

**构建验收建议：**已批准的关键路径有用例覆盖且烟雾测试逐项通过；相关自动套件通过；没有未解决的 Blocker/Critical 缺陷；回归与 Playtest 所需证据完整。任何必测项失败即建议 `FAIL`，证据不全或无法执行建议 `CONCERNS/BLOCKED`，全项满足才建议 `PASS`。这是 QA 的建议性质量门，**是否放行和发布由用户审批**，QA 不代替人工签字。

缺陷严重度使用 `Blocker`（无法启动/关键路径完全中断等）、`Critical`（核心功能严重失效/存档损坏等）、`Major`（重要功能异常但可绕行）、`Minor`（局部显示/体验问题）；最终分级结合实际影响复核，优先级与严重度分别记录。

## 最小记录模板

```text
用例：TC-0001／标题：…
来源：设计/需求链接及验收标准：…（若未定，写“待确认”）
构建/提交、Godot 版本、平台、执行者、时间：…
前置条件及测试数据：…
步骤：1. … 2. …
预期（逐步可观察）：…
实际与证据链接：…
结果：PASS / FAIL / BLOCKED / NOT RUN；关联 BUG-xxxx（若有）：…
```

缺陷单另须写环境、前置条件、可重复的编号步骤、预期、实际、复现频率、严重度、优先级、构建与证据；修复后记录复测结论和回归用例编号。Playtest 另须区分“直接观察”“玩家原话”“分析推断”，避免把单次意见写成普遍事实。
