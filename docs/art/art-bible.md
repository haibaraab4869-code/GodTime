## 2. 视觉锚点

### 2.1 视角约定：按角色类别分层（v4 修订）

原案「纯 2D 横版」决定的是**可玩空间**的方向，不是全部角色的朝向。第二轮（v2）把主角画成**正面 A-pose**（双眼、左右手臂对称朝镜头）是错的：玩家在横版里永远看不到它的正面。但反过来把 NPC 也做成侧视同样是错的——NPC 的职能是**被看见**（对话、交付、给信息），正视图才能同时交代双眼、表情与服饰全貌。

**v4 的分层约定（适用于本项目全部角色资产）：**

| 类别 | 视角 | 画布中的朝向 | 左右侧命名 | `_flip` / `scale.x = -1` | 允许的位移类动作 |
| --- | --- | --- | --- | --- | --- |
| 主角 | 横版侧视 | 面朝 **+x**（右） | `near` / `far` | 允许 | `run` / `dash` / `jump` / `fall` |
| 怪物 | 横版侧视 | 面朝 **+x**（右） | `near` / `far` | 允许 | 同主角 |
| **NPC** | **正视** | 面朝 **+z（垂直纸面向外）** | `left` / `right`（画面左 / 右） | **禁止** | **不做 `run` / `dash`** |

**侧视角色（主角、怪物）的四条硬约定：**

| 项 | 约定 | 违反后果 |
| --- | --- | --- |
| 朝向 | 角色在画布中**面朝 +x（右）** | 朝左只靠 `rig.scale.x = -1`，不另做镜像素材 |
| 面部 | 只出现**一只眼**（近侧），鼻子是脸部轮廓上唯一伸到 +x 的突起 | 画两只眼 = 正面，横版下会显得角色在"看着镜头"走 |
| 命名 | 肢体左右（纵深）用 `near` / `far`；只有「身前 / 身后」才用 `front` / `back`（如 `hem_front` / `hem_back` = 前摆 / 后摆） | 把纵深写成 `front` 会被读成「朝向」；把前后摆写成 `near/back` 又会丢掉方向含义。第二轮的 `arm_front_upper` 是这个错误的实例 |
| 剪影 | 裙摆、腰饰一律向 **-x 拖**，剪影天然左右不对称 | 侧视角色若左右对称，看起来仍像正视图 |

**NPC（正视）为什么成立，以及三条必须守住的边界：**

成立的原因是 NPC **不做横向位移**。侧视与正视的差别主要体现在「跑动/转身时身体如何读」；NPC 站定、被对话、给信息，这层差别不存在，而正视图能多给出表情与正身服饰，收益明确大于代价。

| 边界 | 约定 | 违反后果 |
| --- | --- | --- |
| 命名 | 用 `left` / `right`，以**画面（观众）方向**为准 | 用 `near` / `far` 会引入正视图不存在的纵深概念；用角色自身左右会与观众左右相反，100% 误读 |
| 翻转 | `rig.scale.x` **恒为正**，禁止取负 | 正视图取负 = 左右手互换而脸仍朝镜头，读成「镜像」而不是「转向」。需要转头/侧身时用专用片段（`turn_left` / `turn_right`） |
| 动作 | 不做 `run` / `dash` | 一旦 NPC 需要横向跑动，它**必须改回侧视**——用正视图跑是错的，没有例外 |

**主角专属的一处刻意偏离：脸面按约 75° 近侧视画，不是严格 90°。** 严格正侧脸在 60 px 屏高下只剩一条竖缝（脸宽约 5 px），五官完全不可读。保留约 17 px 颊面后，"一只眼 + 侧鼻"的读法仍然成立，但脸能认出来。这是分辨率所迫的可读性取舍，登记在此，不做隐性处理。

**为什么侧视朝 +x 而不是 -x**：Godot 的 `scale.x = -1` 翻转、以及横版惯用的"右为前"约定（输入正方向、朝向判定、摄像机前瞻）都以此为准。改朝向后 `player.gd` 的 `facing` 语义也要一并翻，代价大于收益。

**NPC 的朝向是 +z，不是 +x**：正视图里「面朝右」没有意义，镜头方向才是它的正面。由此派生一件事——**侧视角色的 `near/far` 与 NPC 的 `left/right` 不能混用在同一套命名体系里**，这也是两套规则分开写、部件名互不复用的原因。

**NPC 是否也用 3 头身**：目前未定（见 §6）。可确定的是它必须与主角处在**同一比例族**内——若 NPC 画成 5 头身写实比例，会把 3 头身的主角衬成"矮子"，破坏世界观一致性。除非设定上刻意要做「高大的神像/巨人」，那属于单独登记的例外。


### 2.2 风格定义：水墨简化

原案只写「2D 水墨」。第二轮（2026-10-26，用户确认）将其落地为 **水墨简化**：

| 层 | 承担内容 | 具体手段 |
| --- | --- | --- |
| 浓墨形体 | 剪影与体块 | 平涂墨色，无渐变、无描边渐变；仅外轮廓 1.1–1.4 px 焦墨线 |
| 纸色留白 | 面部、四肢、交领 | 宣纸白 `#F8F0E3` 打底，形成「墨中留白」 |
| 赭金点线 | 唯一高饱和元素 | 冠、眉间、交领、腰饰、袖口、下摆边 |

- **为什么不用「水墨 + 工笔」（v1 方案）**：工笔细线依赖 40 px 以上的主体高度才有意义。主角在屏上实际只有约 58 px 高（§2.3），工笔层会被缩放到糊成灰块，反而降低动作辨识。故收敛为「色块 + 点线」。
- **这是对「2D 水墨」的收敛，不是替换**：墨色阶、留白、赭金三要素仍是水墨语言。

### 2.3 体型比例

| 项 | 值 | 说明 |
| --- | --- | --- |
| 头身比 | **实测 2.8 头身**（目标 3 头身） | 用户确认 3 头身；侧视发型在下颌以下多占约 4 px，使头高偏大 7% |
| 画布 | 128 × 128 px | 16 个部件共用同一画布坐标系 |
| 身高 | **116 px** | 发顶 `y=4`，脚底 `y=120`（含描边包围盒实测 `y=3..121`） |
| 头高 | **42 px**（发顶 `y=4` 至下颌 `y=46`） | 42 / 116 = **36.2%** |
| 头宽 | **42 px**（`x=43..85`） | 与头高几乎相等——侧视下头是一个圆，不是椭圆 |
| 躯干深度 | **27 px**（`x=52..79`） | 侧视下的"宽度"是身体厚度，比正面窄得多 |
| 头宽 / 躯干深度 | **1.56** | **头明显宽于身体厚度**，这是 Q 版剪影成立的关键 |
| 整体剪影 | 46 × 118 px | 前伸的鼻尖与后拖的裙摆各占一头 |
| 髋 | `y=88` | 所有下肢骨骼的根 |
| 膝 / 踝 / 脚底 | `y=103` / `y=116` / `y=120` | 裙摆止于 `y≈98`（前片）与 `y≈106`（后片） |
| 屏上实际高度 | **约 58 px** | `rig.scale = 0.5`（`game/main.tscn`）|
| 碰撞盒 | 24 × 40 | 角色视觉高度约为碰撞盒的 1.45 倍，头部允许轻微超出碰撞盒 |

**为什么不做 7 头身**：v1 的成人比例在 128 画布里只能画出 48×64 的帧，屏上 24×32，五官与衣褶完全不可读；且与参考品类的少年主角气质不符。3 头身让「一眼认出是主角」靠剪影而非细节。

上表所有墨色是按**纸白底**（`#F8F0E3`）标的。游戏内背景是深夜蓝 `#142032`，底色翻到极暗一侧，整张表就失效了：

| 色 | 对纸白底 | 对深蓝天空 `#142032` |
| --- | --- | --- |

| 焦墨（发）`#13110F` | — | 1.15 |

也就是说：这套配色在概念图（纸白底）上成立，在游戏里不成立。**§2.6 的「任何元素对背景 ≥3:1」铁律优先于本表的色值。**

| --- | --- | --- | --- |
| 袍身 | `#7B7A74` | **3.80** | 替代重墨 `#221F1C` |
| 近侧袖 | `#8A8982` | **4.66** | 保持"比袍身亮一档" |
| 后片裙摆 | `#666560` | 2.80 | 保持比袍身暗 |
| 远侧肢体 | `#585752` | 2.26 | 保持"远侧更浓"（v3 结论不变） |
| 头发 | `#2E2C28` | 1.18 | 仍是画面最暗处，轮廓靠金冠分离 |
| 描边 | `#1C1A17` | 1.06 | 允许糊进天空——亮袍 + 深线才读得出形 |
| 古金 | `#C69E2C` | 6.49 | 不变 |

层级关系（远侧比袍身暗、近侧袖比袍身亮）完全沿用原设计，只是把整条明度轴搬到能过 3:1 的区间。**不要用统一系数缩放墨色**——主体要亮、描边要深，一个系数会同时毁掉两者。

**远侧为什么变"更浓"而不是"更淡"（v3 修订）**：v2 用淡墨 `#3E3933` 表达远侧，那是"空气透视"（越远越淡）的思路。侧视下这是错的——远侧肢体**背光**，应当更暗。v3 改为比袍身更浓的 `#181613`，近侧才受光。反过来做会读成"远侧的手伸到了身体前面"。

**近侧袖为什么要单独一档（v3 新增）**：袖子与袍身原本同色（`#221F1C`），结果挥臂时只有金袖口和白前臂在动，袖子本身看不见，整条手臂读成"飘在胸前的白棍"。给袖子提亮到 `#302C27` 后：

| 对比对 | 相对亮度 | 对比度 |
| --- | --- | --- |
| 近侧袖 `#302C27` vs 袍身 `#221F1C` | 0.0258 vs 0.0140 | **1.81 : 1** |

1.81:1 不足以做"可读性对比"，但足够做**形体分离**——这正是需要的。同理，袖口内侧还加了一道 0.9 px 的受光细线（`p_arm_upper` 中的 hairline）。

**禁用**：高饱和纯红/绿/蓝；渐变色；投影模糊。战斗特效可例外，但须单独规范。

### 2.5 金线的语义

v1 规定「主角身上仅一条金线」。部件拆分后金饰出现在**五个固定位置**，原规则不再成立，修订为：

**金色只允许出现在「权柄相关部位」**：① 冠 ② 眉间朱砂 ③ 交领金线（侧视下落到前襟边缘）④ 腰饰（腰带 + 两条垂带）⑤ 袖口与下摆边。除此之外任何金色都需有设定理由。

对应设定：时衡在「断刻」后仅保留时间权柄，金 = 残存神权的物证。金饰在画布上的面积占比约 7%，是画面中唯一的暖色，因此天然成为视线焦点——这也是它在深色袍子上仍能指示动作方向的原因。

### 2.6 时代区分的色彩规则

`game/world.gd` 两个时代底色：过去 `#202849`（偏暖紫蓝）、现在 `#142032`（偏冷深蓝）。

- 角色**本体配色不随时代改变**，两套底色共用同一套贴图。
- 时代差异由背景、地形、大气承担，不由角色承担。
- 切换时代时播放 `era_switch` 动画（抬头环视 + 布料摆动），用动作而非换色表达「世界变了、我没变」。

#### 实测对比度（2026-10-26，角色静止姿 vs 场景实际色）

| 背景 | 色值 | 相对亮度 | 与角色中位亮度（0.0140）对比 |
| --- | --- | --- | --- |
| 现在·天空 | `#142032` | 0.0141 | **1.00 : 1** ✗ |
| 过去·天空 | `#202849` | 0.0231 | **1.14 : 1** ✗ |
| 地形·现在 | `#657987` | 0.1819 | **3.62 : 1** ✓ |
| 地形·过去 | `#BC8C64` | 0.3037 | **5.52 : 1** ✓ |
| 地台顶边 | `#ECCE9A` | — | 对比度最高，剪影最清晰 |
| 面部亮部 | `#FAEFDE` | 0.873 | 对天空 **12.6–14.4 : 1** ✓ |

**结论与风险（未解决，需决策）**：角色站在地形上剪影清晰（3.6–5.5:1），但**腾空或背景为天空时，深色袍身与底色几乎同亮（1.0–1.14:1），只剩面部、手脚与金饰可见**。这对类银河恶魔城是实质缺陷——跳跃中的落点判断依赖剪影。

候选缓解方案（按侵入性从低到高，均未实施）：

| 方案 | 做法 | 影响 |
| --- | --- | --- |
| A. 提高世界底色明度 | 调 `world.gd` 的 `#142032` / `#202849` | 改动最小，但会削弱「两个时代」的氛围对比 |
| B. 角色加纸色轮廓 | 用 `CanvasGroup` 把 16 个部件合成一层，再套描边 shader | 剪影在任何底色上都分离，是行业标准解法；需改渲染管线 |
| C. 整体提亮袍身 | 把袍身改到 `#4A453E` | 实测对天空仅 1.5–1.7:1，且**降低**地形上的对比（3.62 → 2.12:1），净收益为负，**不推荐** |

在方案确定前，本文档保留当前配色（在地形上最优）并登记该风险。

### 2.7 剪影要求

- 识别锚点（按识别强度排序）：**① 三尖金冠 ② 后拖的袍摆 + 前伸的鼻尖 ③ 左腰两条金垂带**。
- 冠是唯一强于头顶轮廓的元素，因此**任何发饰改动都不得遮挡冠的轮廓**。
- **v3 修订**：v2 遗留的「剪影接近左右对称」问题**已随侧视解决**。侧视本身就不对称：鼻尖在 +x、后脑发团与裙摆在 -x。v2 计划中的「单侧长飘带 + 3–4 根链骨」因此**不再需要**，骨骼预算维持 15 根。
- 避免与已命名角色（白螭、阿蘅、逐光、玉扃、澹台灯、迦蓝、泠祇）剪影冲突；各角色辨识特征应在建立其资产前先登记。**后续角色按 §2.1 分层**：主角与怪物走侧视，剪影靠前后不对称（+x 前伸 / -x 后拖）；NPC 走正视，剪影靠**正身服饰轮廓与头部发饰**，且必须与已命名角色的侧影区分得开。
- **NPC 的剪影判据不同，不能套用主角那套**：侧视靠鼻子与裙摆形成的前后张力，正视图没有这个方向差，只能靠「头饰高度 / 肩线宽度 / 服装开合」三个维度区分。因此 NPC 之间撞脸的概率比怪物之间高，首批 NPC 名单确定时须一次性排开剪影。

## 4. 骨骼与部件结构

### 4.1 为什么必须走骨骼而不是序列帧

AI 图像生成**不能输出骨骼文件**（.tscn/.skel/.json rig）。可用的产出只有位图。因此链路是：

```
确定性绘制 16 张部件 PNG  →  在 Godot 内建 Skeleton2D/Bone2D  →  AnimationPlayer 打关键帧
tools/gen_parts.py            tools/build_rig.gd                tools/build_rig.gd
```

**部件为什么用脚本画，而不是 AI 出图后切分**：第二轮实测过两次 AI 母版（含明确"四肢分离、大缝隙"的提示词），产出都是**四肢与躯干粘连的完整人形**，切出的 16 块是碎片，枢轴无法对齐。骨骼要求每个部件的枢轴与骨骼位置**像素级一致**，这只能靠确定性绘制保证。v3 因为要改成侧视，同一个生成器改坐标即可整体重画——这正是程序化绘制的收益。

### 4.2 骨骼层级（15 根）

```
Skeleton2D  (position = -64, -88，使画布髋点对齐 rig 原点，scale.x 取负时原地翻转)
└── root            (64, 88)  髋，全局根
    ├── torso       ( 0,  0)  袍身，绕髋旋转
    │   ├── head    ( 0,-43)  头，枢轴在颈根 (64,45)
    │   │   └── crown (0,-37) 冠，枢轴在头顶 (64,8)
    │   ├── arm_near_upper (  9,-38) → arm_near_lower (0,17)
    │   └── arm_far_upper  ( -10,-38) → arm_far_lower  (0,17)
    ├── leg_near_thigh (  0, 0) → leg_near_shin (0,15)
    ├── leg_far_thigh  ( -4, 0) → leg_far_shin  (0,15)
    ├── hem_back       (  0,-4) 下摆，前摆也绑在此骨（前后摆同步）
    └── sash_1         ( -6,-8) → sash_2 (-4,5)
```

括号内为**相对父骨骼**的偏移。全部骨骼 `rest = Transform2D(0, position)`，即静止姿态无旋转。

**近远侧的水平偏移是刻意的**：侧视下近侧与远侧肢体在同一条投影线上，完全重合时远侧会被彻底遮住。给远侧 4–13 px 的偏移，它才能在躯干轮廓外露出一点，并在摆动时正确地"从身后探出"。

### 4.3 16 部件 → 骨骼 → z 序

| z | 部件 | 绑定的骨骼 | 枢轴（画布坐标） |
| --- | --- | --- | --- |
| 0 | `leg_far_shin` | leg_far_shin | (60, 103) |
| 1 | `leg_far_thigh` | leg_far_thigh | (60, 88) |
| 2 | `arm_far_lower` | arm_far_lower | (54, 67) |
| 3 | `arm_far_upper` | arm_far_upper | (54, 50) |
| 4 | `leg_near_thigh` | leg_near_thigh | (64, 88) |
| 5 | `leg_near_shin` | leg_near_shin | (64, 103) |
| 6 | `hem_back` | hem_back | (64, 84) |
| 8 | `torso` | torso | (64, 88) |
| 9 | `hem_front` | hem_back | (64, 84) |
| 10 | `sash_2` | sash_2 | (54, 85) |
| 11 | `sash_1` | sash_1 | (58, 80) |
| 12 | `gold_line` | torso | (64, 88) |
| 13 | `arm_near_lower` | arm_near_lower | (73, 67) |
| 14 | `arm_near_upper` | arm_near_upper | (73, 50) |
| 16 | `head` | head | (64, 45) |
| 17 | `crown` | crown | (64, 8) |

z 序不是随手排的，四条硬约束：

1. **远侧肢体必须在袍身之下**（z ≤ 3 < 8），否则会像贴在胸前的贴纸。
2. **近侧腿必须在裙摆之下**（4,5 < 6,9），否则大腿会穿出裙子。侧视下这条比 v2 更关键——正面有两条腿分列两侧，侧视只有一条腿在裙正后方。
3. **近侧前臂必须在近侧袖口之下**（13 < 14），否则手会盖住金袖口。
4. **近侧臂必须在袍身之上**（13,14 > 8），手臂才读得出在身体前面。

### 4.4 绑定方式：刚性绑定，不做权重蒙皮

每个部件 = 1 个 `Sprite2D`，作为 1 根 `Bone2D` 的子节点，整块刚性跟随；**不使用** `Polygon2D` 权重蒙皮。

- **理由**：3 头身 + 平涂墨色没有任何渐变，蒙皮形变在平涂色块上会产生肉眼可见的拉伸与褶皱错位；刚性块状跟随反而更接近剪纸动画 /《空洞骑士》的观感。
- **代价**：关节处没有平滑过渡。缓解手段是部件之间**故意重叠 2–4 px**，且袖根向躯干内侧多伸 1.8–2.2 px（见 `tools/gen_parts.py` 的 `p_arm_upper` 的 `ext` 参数），保证抬臂 78° 时肩部仍不露缝。
- **副产品**：近侧前臂与袖共用同一个肘部枢轴，且前臂贴图的上端画到枢轴**之上** 3.8 px。两者在枢轴处必然重叠，因此任何角度下都不会脱开——这是几何上的保证，不是靠调数值凑的。

### 4.5 枢轴规则（违反即静止姿错位）

```gdscript
sprite.centered = false
sprite.offset   = -pivot      # pivot 为画布坐标
```

- 部件贴图按**画布绝对坐标**绘制，枢轴即该部件在画布中的关节点。
- `sprite.offset = -pivot` + `centered = false` 使贴图原点正好落在骨骼位置。
- **要求**：`PART_MAP` 里的 pivot 必须与 `BONES` 推出的画布坐标一致。`tools/verify_rig.gd` 会逐项断言偏差 < 1 px，目前 0 项失败。

### 5.2 方向与符号约定（v3 重写，必读）

Godot 2D 的 `rotation` 正值在屏幕上表现为**顺时针**；代入 y 轴向下可推出两条相反规则：

| 骨骼朝向 | 例 | 正角度的效果 |
| --- | --- | --- |
| 朝**下**（+y） | 四肢、腰饰、裙摆 | 末端摆向 **-x** ⇒ **向后** |
| 朝**上**（-y） | 躯干、头、冠 | 顶端摆向 **+x** ⇒ **前倾** |

所以：**「布料向后拖」= 正角度；「身体前倾」= 正角度；「后仰」= 负角度。**

两个已被踩中的反例，写在这里防止重犯：

- v1 的腰饰关键帧用了**负**角度，等于让布料**向前飘**——跑起来像在倒着走。v3 全部为正。
- 侧视跑动最容易被误写成"正面跑"：如果大腿振幅只有 ±10°，侧视下几乎看不出跨步。v3 把大腿振幅定在 **±26°**（小腿只负责折叠，始终为正）。

### 5.3 布料跟动

`hem_back` 与 `sash_1/sash_2` 都有独立骨骼与动画轨道，不是焊死在躯干上：

- `hem_back` 同时驱动前摆（`hem_front` 绑同一根骨），所以裙摆整体摆动。侧视下整幅裙摆一起向 -x 甩，正是侧视跑动最主要的动感来源。
- 摆动幅度随动作强度递增：idle 1–3° → run 15–25° → fall 22–28° → dash 26–30° → 腰饰最高 48°。
- `tools/verify_rig.gd` 断言 run/fall/dash 的下摆必须实际摆动（最大偏移 > 0.05 rad），避免「裙子像木板」的回归。

### 5.4 动画状态机（`game/player.gd`）

- 优先级：`hurt`(5) > `attack`(4) > `dash`(3) > `land`(2) > `turn`/`era_switch`(1)。低优先级不能打断高优先级的一次性动作。
- 一次性动作由 `_override_left` 计时器控制，到期后回落到 `_pick_locomotion()` 选择的 `idle/run/jump/fall`。
- 朝向翻转取 `rig.scale = Vector2(RIG_SCALE * facing, RIG_SCALE)`，`RIG_SCALE = 0.5`。
