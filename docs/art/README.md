## 素材与文档分离

- `docs/art/`：决策、参考链接、生产规格和资产登记；不要将仅供参考的第三方作品当作可交付游戏素材。
- 实际素材存放于 `res://assets/`。该目录于 **2026-10-26 经用户授权启用**，当前唯一使用者为主角资产。

## 路径与命名规则

> v1 的四条规则（A–D）针对「立绘 + 纵向分层」方案。第二轮改为骨骼绑定后 A、C、D 已重写；第三轮改为横版侧视后新增 G；第四轮按角色类别把视角拆成两档（主角/怪物 = 侧视，NPC = 正视），规则 G 据此重写。适用目录统一为 `assets/characters/`（含主角、怪物与 NPC）。

### 已生效规则（2026-10-26 第三轮起）

**规则 A：按角色/对象建目录，内部分「部件 / 骨骼 / 评审」三类。**

```
res://assets/
└── characters/
    └── <object_id>/          对象标识，小写英文，与 docs 中的角色名对应
        ├── parts/            16 张部件贴图 + parts.json（引擎引用）
        ├── rig/              骨骼场景 .tscn（引擎引用）
        └── preview/          评审图（引擎不引用）
```

- **适用范围**：`assets/characters/` 下全部角色。未来 `environments/`、`ui/`、`vfx/` 是否需要 `rig/` 按其资产形态再定，不预先建空目录。
- **变化说明**：v1 的 `source/`、`layers/`、`export/`、`spec/` 均已删除。`source/` 删除因为新链路是程序化绘制、不再有 AI 母版；`export/` 删除因为成品是骨骼场景而非序列帧；`spec/` 的规格数据改由 `parts.json` 机器可读持有。

**规则 B：场景与脚本只引用 `parts/` 与 `rig/`，不引用 `preview/`。**

- **适用范围**：`assets/characters/` 全部。`preview/` 里的评审图单张可达 2.3 MB，导入后会被打进构建包，纯属浪费。
- 若场景引用了 `preview/`，视为资产规范违规，须在美术评审中记录（`verify_rig.gd` 不覆盖此检查）。

**规则 C：命名格式 `char_<对象>_part_<部件名>.png`，不含密度后缀。**

- 示例：`char_shihung_part_arm_near_upper.png`
- **部件名必须与骨骼名完全一致**：`build_rig.gd` 用 `"char_shihung_part_%s.png" % part_name` 拼路径，改名即断链。
- **取消 `@2x` / `@4x`**：部件只保留一套 128×128 源，缩放由 `rig.scale` 在引擎内完成。v1 的密度后缀规则作废。
- 小写英文与数字、下划线分词；中文名不入文件系统，避免跨平台编码问题。
- `icon.svg` 不改名（Godot 默认图标，改名会破坏 `project.godot` 的 `config/icon` 引用）。

**规则 D：每个部件只出一套，以骨骼画布为基准，不做密度副本、不做纵向分层。**

- 部件按**画布绝对坐标**绘制，枢轴即该部件在画布中的关节点；`Sprite2D.offset = -pivot` 使贴图原点落在骨骼位置。
- 枢轴与骨骼位置的偏差由 `tools/verify_rig.gd` 断言（阈值 1 px）。
- **适用范围**：任何需要骨骼绑定的角色资产。

**规则 E（新增）：每个角色只保留一套骨骼 rig；换方案时删除旧 rig 与旧部件。**

- 并行保留会导致「不知道哪套是当前版本」，且 `parts/` 的部件名会互相覆盖。
- 删除必须在 [资产登记 §6](asset-manifest.md) 留记录，写清删了什么、为什么删。

**规则 F（新增）：部件贴图的生成脚本入库，贴图本身视为可重建产物。**

- 部件由 `tools/gen_parts.py` 确定性绘制，同一脚本重跑得到逐像素相同的输出。
- 因此评审意见应落到脚本参数上，而不是手工修图——手工修图会在下次重跑时丢失。
- 第三轮改视角时，只改 `gen_parts.py` 与 `build_rig.gd` 的坐标常量就整体重画了 16 个部件与全部动画，这条规则的价值在此得到验证。

**规则 G（第四轮重写）：视角按角色类别分层——主角与怪物画横版侧视，NPC 画正视。**

| 类别 | 视角 | 朝向基准 | 左右侧命名 | 是否可用 `rig.scale.x = -1` 翻转 |
| --- | --- | --- | --- | --- |
| 主角 | 横版侧视 | 画布中面朝 **+x** | `near` / `far`（近侧 / 远侧） | 是 |
| 怪物 | 横版侧视 | 画布中面朝 **+x** | `near` / `far` | 是 |
| **NPC** | **正视（面向镜头）** | 画布中面朝 **+z（垂直纸面向外）** | `left` / `right`（画面左 / 右） | **否** |

- **依据**：立项案「纯 2D 横版」决定主角与怪物必须是侧视——玩家在横版里永远看不到它们的正面。NPC 不是这个逻辑：NPC 的作用是**被看见**（对话、交付、给信息），正视图能同时呈现双眼、表情与服饰全貌，这是横版游戏里 NPC 的通行做法，也是唯一能用一张图交代「这个人是谁」的方向。
- **为什么必须写进规则**：违反时贴图仍能正常加载、动画也照跑，不会报任何错——只能靠外观检查发现。第二轮的 `arm_front_upper` 就是这么一路错到交付才被看出来的。
- **适用范围**：`assets/characters/` 下全部角色。新增 NPC 时同样按规则 A 的三分目录（`parts/` / `rig/` / `preview/`）建，但视角与命名走 G-2。

**G-1：侧视角色（主角、怪物）两条细则**

- 朝左**不另做素材**，由 `rig.scale.x = -1` 处理。只有确实需要双面差异时才在[资产登记](asset-manifest.md)登记例外。
- 侧视里 **`front` / `back` 只能用来表达「身前 / 身后」，不能用来表达「身体左右侧」**。前者是角色朝向的前后（沿 +x/-x 轴），后者是纵深（垂直纸面），侧视下把纵深写成 `front` 会被读成「朝向」，是持续性误导。
  - **合法**：`hem_front` / `hem_back`（前摆 / 后摆，指裙摆在身前还是身后）。
  - **禁止**：`arm_front_*` / `leg_front_*` / `arm_back_*` / `leg_back_*`（肢体左右是纵深，应写 `arm_near_*` / `leg_far_*`）。第二轮的 `arm_front_upper` 因此全部改为 `arm_near_upper`。
  - **判据**：前缀是 `arm_` / `leg_` 一律用 `near` / `far`；前缀 `hem_` 用 `front` / `back` 区分前后摆；`sash_` 按序号 `sash_1` / `sash_2`（同一根腰饰的两段），不涉及前后。
  - `tools/verify_rig.gd` 会自动检查这一条（对 `arm_front*` / `leg_back*` 等前缀报错）。

**G-2：NPC 三条细则（第四轮新增）**

- **命名用 `left` / `right`，以画面（观众）方向为准**，即「观众看到的左侧」。禁止在 NPC 资产里使用 `near` / `far`——那是侧视的纵深概念，正视图没有纵深差别。
- **NPC 的 rig 禁止水平翻转**。`rig.scale.x` 必须恒为正：正视图一旦取负，角色的左右手会互换，而脸仍然朝着镜头，等于把「镜像」读成「转向」。NPC 需要表现「转头/侧身」时用专用动画片段（如 `turn_left` / `turn_right`），不用翻转实现。
- **NPC 不做的动作**：`run` 与 `dash`。NPC 不做横向位移，侧视跑动的读法问题对它不存在；它的核心片段是 `idle` + 交谈。这条差异是「NPC 可以用正视」成立的前提——如果将来的 NPC 需要横向跑动，它必须改回侧视，不允许用正视图跑。

**G-3：视角在资产元数据里显式声明**

- `parts/parts.json` 必须带三个字段：`view_class`（只允许 `"side"` / `"front"`）、`view`（人类可读描述，如 `"side, facing +x"` / `"front, facing camera"`）、`flippable`（布尔，NPC 必须为 `false`）。
- 用途：以后加 NPC 时，生成器与校验脚本可以按 `view_class` 分支，而不是靠猜路径或看图。
- 违反 `view_class` 与实际画法不一致时，`tools/verify_rig.gd` 无法发现（它只校验主角），必须靠评审图。因此**新增任何角色资产时，评审图是必交项**（见规则 B）。

## 资产登记要求

| 字段 | 填写要求 |
| --- | --- |
| 资产 ID / 名称 / 类别 | 唯一可检索标识；注明角色、场景、UI、特效等实际用途 |
| 状态 / 负责人 / 日期 | 需求、草稿、可用（内部）、待审、批准、入库等状态及更新时间 |
| 需求依据 / 使用场景 | 指向已确认的设计文档及具体使用位置；未知则标「待确认」 |
| 视觉规格 | 风格规范版本、视角、画布尺寸、体型比例、色彩值、动画片段清单 |
| 技术规格 | 生成脚本、导出格式、导入设置、绑定骨骼、z 序、性能预算 |
| 来源 / 作者 / 授权 | 自制、委托、商用素材、AI 辅助等；保存来源链接、许可证名称或合同凭证、许可范围及署名要求 |
| AI 辅助记录 | 如使用，记录模型/工具、提示词或制作流程、参考素材来源及商用与再分发许可核验结果 |
| 验收 / 引用 | 审核人、批准版本、实际 `res://` 路径、关联场景、回归测试与对比度检查结果 |

**授权底线：**未能核实来源和项目所需的使用、修改、商用及分发权限的素材，不进入正式资源库；"网上找到"或生成得到均不等于已获授权。参考图与可发布资产分开登记。AI 生成资产的商用范围须由项目负责人依所用服务条款确认。

## 方向决策与验收

以下问题**已确认**（2026-10-26，用户通过选项或指令确认）：

| 决策项 | 选定 | 确认轮次 |
| --- | --- | --- |
| **视角（主角）** | **横版侧视，面朝 +x**（`front/back` 命名改为 `near/far`） | 第三轮（指令） |
| **视角（怪物）** | **横版侧视，面朝 +x**，与主角同一套约定 | 第三轮提出，第四轮重申并要求落为规则 |
| **视角（NPC）** | **正视，面向镜头**；命名 `left/right`、禁止水平翻转、不做 `run`/`dash` | 第四轮（指令） |
| 体型比例 | **3 头身**（画布 128×128，身高 116 px，屏上约 58 px，实测 2.8 头身） | 第二轮 |
| 风格特征 | **水墨简化**（浓墨形体 + 纸色留白 + 赭金点线） | 第二轮 |
| 部件结构 | **16 部件**刚性绑定到 15 根骨骼 | 第二轮 |
| 动画需求 | **11 项全套**（idle/run/jump/fall/dash/attack/hurt/respawn/turn/land/era_switch） | 第二轮 |

以上取代 v1 的「7 头身 / 水墨+工笔 / 5 层纵向分层 / 立绘+游戏帧」。详见[美术圣经](art-bible.md) §2.1、§3.2。

以下仍**待确认**：

| 问题 | 影响 | 优先级 |
| --- | --- | --- |
| **天空底色下角色剪影对比度仅 1.0–1.14:1** | 腾空与开阔场景的动作辨识；类银河恶魔城里这是实质缺陷 | **阻塞**：需在「提高世界底色明度」与「加 CanvasGroup 描边」之间决策 |
| **怪物资产尚未制作** | 侧视约定已定（规则 G），但还没有资产落地；`training_dummy.gd` 仍是 `_draw()` 矩形占位 | 高：需先定首批敌人名单 |
| **NPC 资产尚未制作，名单未定** | 正视约定已定（规则 G-2），但无资产、无名单，`view_class = "front"` 从未被实际验证过 | 高：需先定首批 NPC 名单与对话需求 |
| **NPC 正视图与横版场景的空间一致性** | 正视图人物站在侧视场景里，玩家会读成「他正对着我」，这需要美术与关卡一起确认站位方式（是否固定在门前/柜台后、是否禁止横向走动） | 中：NPC 名单确定后与关卡一并定 |
| NPC 部件数与骨骼预算 | 正视图左右对称，理论上可以用更少部件（8–12）与更少骨骼，但对称也让左右手互相遮挡 | 中：首个 NPC 定稿时确定 |
| 脸面采用约 75° 近侧视（非严格 90°） | 严格正侧在 58 px 高下只剩一条竖缝，五官不可读 | 高：需美术负责人认可该取舍 |
| 「水墨简化」是否被接受为原案「2D 水墨」的落地形式 | 后续所有资产的风格基准 | 高 |
| 目标平台分辨率与整数倍缩放 | 当前 `rig.scale = 0.5` 是原型值，非最终值 | 中 |
| 可访问性目标 | 对比度门槛、降低闪烁要求 | 低（随 `accessibility.md` 一并定） |
| 素材授权边界（含未来若引入 AI 生成内容的商用范围） | 能否进入正式资源库、能否对外发布 | 低（当前资产为程序化绘制，无此风险） |

> ~~是否需要补回单侧长飘带~~ —— **已关闭**。第二轮登记该问题是因为正视图左右对称；改为侧视后鼻尖、后脑发团、拖尾裙摆天然形成不对称剪影，链骨方案不再需要，骨骼预算维持 15 根。

视觉信息不能只靠颜色区分；UI 状态应同时考虑形状、文字或图标，最终对比度、字体缩放与降低闪烁/运动的要求以确认后的可访问性规范为准。
