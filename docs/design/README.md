## 文档职责与工作流

1. **立项案是设计基线**：每项设计标注立项案对应章节/页码，逐条核对一致性；功能文档只链接来源，不复制长段原案，也不擅改原 DOCX。无法定位、原案未明确、拟扩展或与原案冲突时，标为“待确认”，不得视为获批规则。
2. **单一功能规格回答“怎么做/如何验收”**：每项系统或玩法建一份文件，使用[功能设计模板](feature-template.md)写清触发与输入、状态与规则、数据公式、边界、界面反馈、依赖及测试可判定的验收标准，并附基线对照与偏差登记。文件建议命名 `feature-<简短标识>.md`，链接放在下表。
3. **偏差审批是定稿前置条件**：确需偏离立项案时，逐项登记原案依据（章节/页码）、拟议偏差、原因、对功能/美术音频/工程/测试的影响、备选方案及审批人结论；与其他已批准功能或技术约束冲突也须注明双方位置并提交评审。**用户明确批准前，不得定稿、排期或实现偏差内容**；未经确认不以新规格覆盖原案。
4. **变更可追踪**：获批后调整规则时更新版本、日期、变更摘要、批准依据和受影响的链接，通知相关实现与测试负责人；未解决问题不得写成既定结论。
